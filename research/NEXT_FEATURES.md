## 提案する機能（優先度順）

優先度は「**今あるものの価値を引き出す**」→「**使われ方を知る**」→「**規模を広げる**」の順。
新規ソースの追加は既に飽和気味（反証で出尽くしを確認済み）のため、上位に置かない。

### ★★★ A. 使った結果を記録して在庫を育てる（最優先）

**課題**: 現状は「提案して終わり」。どのループが実際に使われ、成功したかが残らない。
在庫は増えたが、**どれが効くか**の情報がない。

| 機能 | 内容 |
|---|---|
| A-1 実行記録 | ループを使った結果（成功/失敗・停止理由・反復回数・所要時間）を記録する。`.loop/runs.jsonl` 形式 |
| A-2 停止理由の集計 | どの停止条件で止まったかを集計（成功/回数上限/予算/無進展/異常）。記事の「停止理由の記録」に対応 |
| A-3 実績バッジ | 実行回数・成功率をループカードに表示。「よく使われる」「成功率が高い」が一目で分かる |

**なぜ最優先か**: ループエンジニアリングの要は「回して改善する」こと。
記録がないと、1,354本のうちどれが有効かを永久に判断できない。
また A-2 は記事が明示する運用要件（「どの条件で止まったかを残す」）そのもの。

**実装規模**: 中（記録スキーマ + 集計画面 + カード表示）

---

### ★★★ B. ループの組み合わせ（スタッキング）

**課題**: 現状は1ループ単位。実務では「CI修復 → PRレビュー → リリースノート」のように
連鎖させたい。LE の在庫にも `stacking-loops` の概念が含まれている。

| 機能 | 内容 |
|---|---|
| B-1 ループ連結 | 複数ループを順序付きで束ね、1つの手順書として書き出す |
| B-2 入れ子構造 | 「時間型の外側ループ」×「ゴール型の内側ループ」の入れ子（AW が示す `/loop` が `/goal` を包む形） |
| B-3 連結テンプレ | よくある組み合わせを既製品として用意（例: 朝のトリアージ一式） |

**実装規模**: 中（お気に入り機能を拡張すれば土台は流用可能）

### ★★ C. 案件への適用を助ける

| 機能 | 内容 |
|---|---|
| C-1 案件プロファイル | 「使っているツール（Claude Code / Cursor / Codex）」「言語」「CI」を設定すると、合わないループを除外・コマンドを自動置換 |
| C-2 スキル一式の書き出し | 選んだ複数ループを `.claude/skills/` の**ディレクトリ構造ごと** zip で出力（現在は1ファイルずつ） |
| C-3 導入チェックリスト | 記事の「稼働前に決めること」（責任者・上限・証拠の形式・停止理由の記録・ロールバック手段）を埋める様式 |

**実装規模**: C-1 中 / C-2 小（JSZip 追加が必要） / C-3 小

現在 3種のイベントを記録しているが、**見る画面がない**（`insights.html` は別作業で追加済み）。

| 機能 | 内容 |
|---|---|

|---|---|

## 推奨する進め方

```
第1弾: A（実行記録・停止理由の集計）＋ D（計測の可視化）
        → 「どのループが効くか」が分かる状態にする。データは既に一部ある
第2弾: B（ループの組み合わせ）＋ C-2（スキル一式の書き出し）
        → 実務の単位に合わせる
第3弾: F（鮮度維持の自動化）＋ E-1/E-2（体裁）
        → 運用の手離れ
```

**E-3（1,126本の手書き）は最後**。工数が大きく、A/D で「どのループが実際に使われるか」が
判明してから対象を絞る方が効率的。全部を磨くより、使われる100本を磨く。

## 提案しない（やらない）こと

| 項目 | 理由 |
|---|---|
| 新規ループポータルの追加 | 敵対的反証で出尽くしを確認済み。ailooplibrary 等は再配信、autoresearch 系は実装でありカタログではない |
| ループの自動実行機能 | 本ダッシュボードは「設計図の配布」が役割。実行は Claude Code / Cursor 側の責務。混ぜると停止条件の責任境界が曖昧になる |
| AI によるループ自動生成 | 既に1,354本あり、カスタマイザーで改変もできる。生成物の品質保証コストが見合わない |
